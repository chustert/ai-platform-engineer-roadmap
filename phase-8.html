Phase 08 · months 7–9

Evaluation engineering

Outcome

Turn subjective "it seems better" judgments into repeatable datasets, metrics and release gates that catch regressions before users do.

Evals are tests for behaviour

Unit tests remain necessary but are insufficient for probabilistic systems. Evaluation engineering asks whether the whole system succeeds on representative tasks. The dataset becomes one of the platform's most valuable assets because it encodes what the organisation means by good behaviour. In an AI-native team, evals are also how you trust agent-written changes to agent systems.

Layered evaluations

Use deterministic assertions where possible: schema validity, required citations, tool arguments, forbidden actions, exact retrieval targets. Add human review for ambiguous quality. Use model-based judges for scale, calibrated against human labels and never treated as ground truth.

Metrics and thresholds

Precision, recall and false positives/negatives for classification-like behaviour; selection and argument accuracy for tool use; recall at k and ranking measures for retrieval; task-specific rubrics end to end. Track cost and latency alongside quality.

Regression workflow

Every meaningful production failure is a candidate eval case: reproduce, minimise, label, fix without damaging the broader suite. Run a representative subset in pull requests and larger suites before deployment.

Build: two benchmarks

An answer-quality benchmark for your product from real queries and complaints that gates every prompt or model change. And a PR-review benchmark of clean PRs, obvious and subtle bugs, architecture violations and false-positive traps, labelled with expected findings. Compare prompt/model/workflow versions with comparable experiment records.

Exit milestone

You can reject a prompt or model change because measured quality regressed, identify which cohort failed and show whether the regression came from retrieval, reasoning, tool use or aggregation.
