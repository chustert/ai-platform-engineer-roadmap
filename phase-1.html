Phase 01 · months 0–2

AI-native engineering workflow

Outcome

Get reliable, reviewable output from coding agents at high throughput – several at once – and understand the resulting code well enough to own it in production.

Why this phase comes first

Everything else in this roadmap will be built by agents under your direction, so the quality of that direction is the multiplier on every later phase. It is also a direct job requirement: one posting says "drive AI coding agents hard, review what they give you, own what you merge"; the other wants someone to drive org-wide adoption of Claude Code and MCP. You cannot lead adoption of a workflow you have not mastered.

Master one agent deeply, know the rest

Go deep on one coding agent – Claude Code is the obvious choice given the Staff posting names it – and learn enough of the others (Codex, Cursor, OpenCode) to compare them honestly. Depth means the configuration surface, not just prompting:

  • Project context files (CLAUDE.md / AGENTS.md): what belongs in them, how to keep them short and current.
  • Plan-first and spec-first work: have the agent propose a plan, correct it, then execute.
  • Skills, custom commands and subagents: packaging repeatable know-how so agents (and colleagues) reuse it.
  • Hooks: enforcing formatting, tests, secret scanning or policy automatically around agent actions.
  • MCP servers: giving agents controlled access to tickets, docs, logs and databases.
  • Permission modes and sandboxing: what the agent may do without asking, and where it runs.
  • Headless and CI use: running the same agent non-interactively in pipelines, and the Claude Agent SDK as the programmable version of that loop (the foundation for Phase 5).

Parallel agents and the supervision layer

The step change in throughput comes from running several agents at once – one on a feature, one on tests, one investigating a bug – without them trampling each other or silently stalling. That needs three things: isolation (a git worktree or container per agent), visibility (which agent is working, blocked waiting for approval, or idle), and persistence (sessions that survive a closed laptop or dropped SSH connection).

A new category of tools has grown up around exactly this. Herdr is a good example worth learning: an open-source, agent-aware terminal multiplexer that runs Claude Code, Codex, Cursor or OpenCode side by side, shows each agent's state, keeps sessions alive on local or remote machines, and exposes a socket API that lets agents spawn and prompt other agents. tmux or Zellij with git worktrees covers much of the same ground with more maturity and less agent awareness.

On Herdr and tools like it

Learn it, use it, but do not build your identity on it. At the time of writing Herdr is pre-1.0 (v0.4), maintained mainly by one developer and has no built-in process sandboxing; this category is moving monthly, and coding agents are absorbing some of it natively. The durable lesson is the pattern: isolate, observe, persist, and gate risky actions. That is the same supervisor problem you will solve at platform scale in Phases 5 and 11 – Herdr is the one-person version of it.

Verification discipline

Make the agent's work checkable before you look at it. Require tests with every change, but review the test intent yourself – agents readily write tests that pass without proving anything. Lean on types, linters, CI and short feedback loops so the agent can verify its own work. Review by risk (see "Read fluently, write rarely"), and keep a log of the defects you caught and missed; it tells you where your review is weak.

Build: a raw agent service – directed, not typed

Write a one-page spec, then have your coding agent build a small FastAPI (or TypeScript) service that talks directly to one model API and implements the tool loop itself: accept a task, call the model, validate any requested tool call, execute it, feed the result back, stream the final response. No LangChain or LangGraph yet – you want the mechanics visible. Persist runs to Postgres with model, prompt version, tokens, tool calls, duration and outcome. Add Docker, health endpoints, bounded retries, timeouts and CI.

Then do the part that builds understanding. Draw the loop as a sequence diagram from memory. Inject five failures (model timeout, malformed tool arguments, duplicate request, cancellation, a tool that hangs), predicting each outcome before you run it. Find the seeded bugs an agent plants for you. This is where the "knowing code" from the previous section comes from.

Build: your personal agent platform

Write down the workflow you converge on – context-file conventions, two or three skills, a few hooks, a worktree-plus-multiplexer setup and a review checklist – as a small repository someone else could clone. This is the seed of Forge and of the adoption work in Phase 12.

Exit milestone

You can go from a written spec to a deployed, tested service in a day using agents, while running at least three agents in parallel without losing track of them. You can explain every step of the agent loop, predict how it fails, and find planted bugs in an agent-written diff. Another engineer could adopt your agent setup from its README.
