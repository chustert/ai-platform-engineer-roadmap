Beyond the phases

12-month execution plan

The phases overlap. Use the table as a scheduling scaffold, not a rigid dependency graph. Keep one evolving codebase (plus your product) so later phases harden earlier work rather than starting over.

MonthPrimary focusProof / deliverable
1AI-native workflowAgent setup (skills, hooks, MCP), parallel agents with worktrees + multiplexer, raw agent service
2Workflow + code literacy + LLM systemsFault-injection write-up, seeded-bug reviews, published agent setup, cost tracing
3Economics + retrievalModel router and gateway ADR; product cost per task; retrieval eval set from real queries. Apply-ready for AI-native product roles
4Context engineering + MCPHybrid and agentic search compared; engineering and product MCP servers
5Agent architecture + durable executionStateful PR reviewer on Temporal; headless coding agent in CI
6AWS foundationIaC, queues, durable worker, reviewed IAM
7AWS + observabilityBedrock integration, OTel traces, ops dashboard incl. coding-agent usage
8EvaluationsProduct and PR-review benchmarks, CI gates
9SRE + securitySLOs, budgets, replay, game day; threat model, sandbox comparison, injection suite, supply-chain case study
10Platform + DevExForge slice, SDK/CLI, shared agent config, one-command local
11Adoption + capstone hardeningPairing-led adoption effort, second agent, onboarding test, runbooks
12Staff artifacts + portfolioRFCs, ADRs, cost report, case studies, mock system design. Apply-ready for senior/Staff platform roles

Suggested weekly allocation (about 9 hours)

  • 2.5 hours – direct agents to build the main system (often several in parallel).
  • 2 hours – targeted study tied to the current build problem.
  • 1.5 hours – verification: read diffs, run evals, inspect traces, seeded-bug review.
  • 1 hour – break something: failure injection, cost or security probing.
  • 1 hour – write an ADR, notes, runbook or case study.
  • 1 hour – improve your agent workflow (a new skill, hook or context fix) and retrospective.

Quarterly checkpoints

At the end of months 3, 6, 9 and 12, stop adding features for a session and review the whole system. Is the architecture getting easier or harder to change? Is spend predictable? Is failure diagnosis improving? Does the eval set reflect failures you have actually seen? Is your agent tooling list still current? Delete or simplify abstractions that are not earning their complexity.

How to adjust the pace

If a phase takes longer, move on only when the exit milestone is real. Do not compensate by skipping observability, evals or security; those distinguish platform engineering from prototyping. If you are ahead, deepen the same system with real users, stricter SLOs, another team or a second agent rather than starting unrelated demos. If you land an AI-native role early, re-map the remaining phases onto that job's systems – that is better evidence than anything built on the side.

Every three months, publish a progress note

One page: what you built, what failed, one architecture decision you changed your mind about, the most important before/after metric, and the next risk. These notes become unusually strong interview material because they show judgment developing over time.
