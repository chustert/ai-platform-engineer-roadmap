Phase 04 · months 3–5

MCP and production tool systems

Outcome

Expose capabilities to agents through controlled, observable, least-privilege interfaces rather than giving models arbitrary application or shell access.

Why tools matter

Agents become operationally interesting when they can act, so tool systems sit on the security and reliability boundary. A model may suggest an action; your tool layer owns validation, authorization, idempotency, timeouts, auditability and side effects.

MCP as a protocol

Learn MCP as a protocol, not only as configuration: client/server boundaries, tool and resource discovery, transports, schemas, authentication and lifecycle. Have agents build both a client and a server, then inspect the real messages and failure cases yourself (the MCP Inspector helps) so the abstraction never becomes a black box.

Tool contract design

Make tools narrow and intention-revealing: prefer create_pull_request(base, head, title, body) over run_shell(command). Validate every argument server-side. Classify tools as read, execute, write and privileged; privileged operations should require an approval token or a separate service identity. Design tool outputs for a model reader – concise, structured, with actionable errors.

Security and tenancy

Propagate user or workload identity. Use scoped, short-lived credentials and explicit authorization checks. Log who or what requested an action, the validated arguments, the side effect and the result. Never let a model select its own role or bypass policy because it claims urgency.

Distribution to teams

An MCP server nobody installs has no impact. Learn how servers are packaged and distributed to a team alongside shared skills and settings (for example as Claude Code plugins or managed configuration), versioned and updated safely. This is the mechanics behind "drive adoption of custom MCP implementations".

Build: two MCP servers

An engineering server exposing search_code, get_pr, get_build_status, get_logs, run_tests, create_branch and open_pr, with rate limits, audit logs, cancellation, structured errors and per-tool permissions; destructive actions opt-in and approval-gated. And a server that exposes your product's core capability to other people's agents – a real product feature as well as a learning exercise.

Exit milestone

You can design a tool API that an agent uses reliably, explain its trust boundary, show that malformed or malicious model output cannot bypass validation or authorization, and roll the server out to other people's agents.
