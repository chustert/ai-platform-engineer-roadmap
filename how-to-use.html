How to use this roadmap

This document is a curriculum, not a reading list. The objective is to create evidence that you can operate production AI systems, not merely talk about them. Every phase therefore combines theory with a build target, operational requirements and an exit checklist. You should be able to point to working software, traces, evals, dashboards, runbooks and design decisions at the end of each stage.

This roadmap assumes the way software is now built: coding agents write most of the code, and you direct, verify and own it. That changes what you practise. Typing syntax is no longer the bottleneck; knowing what to build, specifying it precisely, recognising when output is wrong, and running the result in production are. Every build target below is written with that in mind: you direct the build, then you prove you understand what was built.

The sequence

It starts with the AI-native engineering workflow itself, because every later phase depends on it and because both target roles ask for it directly. It then moves through model economics, context and tool systems, orchestration, cloud, observability, evaluations, reliability and security, and only then asks you to build a reusable platform. That order prevents a common failure mode: learning frameworks before learning the engineering problems those frameworks are trying to hide.

Recommended pace

The default pace assumes roughly 8–10 focused hours per week outside normal work, over about 12 months. With agents doing most of the implementation, build work that once took 18 months compresses; what sets the pace now is understanding and operating what you build. If your day job exposes you to the same material, count that time: the goal is competence, not calendar compliance. Phases overlap by design; for example, you add tracing in Phase 1 even though observability becomes a dedicated topic later.

The evidence rule

For each concept, ask: what artifact proves I can do this? A certificate is weak evidence. A deployed service with a cost dashboard, regression suite, failure-mode tests and a written architecture decision is strong evidence. Real users are the strongest evidence of all, which is why this roadmap routes as much work as possible through a real product with real users (see "Your proving ground").

The standard to aim for

You are not trying to become the person who knows the most AI libraries, or the person who types the most code. You are trying to become the engineer other teams trust to make autonomous software reliable, economical, observable and safe – including the coding agents they use every day.

Your progression

  • Stage A – Builder: ships useful AI-powered products quickly by directing coding agents well.
  • Stage B – Operator: runs them in production and diagnoses failures from evidence.
  • Stage C – Platform engineer: makes the capability reusable by other teams.
  • Stage D – Staff engineer: sets technical direction, creates standards and drives adoption without relying on authority.
