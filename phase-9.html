Phase 9 · Months 8 to 10

Run agents reliably in production

Outcome

You run agents as distributed production workloads, with SLOs, limits on failure, planned fallbacks, and practised incident response.

Define reliability in terms the user sees

An agent can return HTTP 200 and still fail the task, so availability is not enough. Define service level indicators, or SLIs, for completed tasks, quality, latency, and cost. Examples are the rate of answers with valid citations, the rate of severe false positives, p95 latency, and the cost of each answer.

Plan for partial failure

Learn circuit breakers, retries with limits and random jitter, concurrency limits, load shedding, dead-letter queues, handling of jobs that keep failing, idempotency, and replay. Plan for partial failures explicitly. The model call succeeds but the tool fails. The tool succeeds but the response is lost. The worker dies after it creates a branch but before it records that the job finished.

Stop runaway runs

Give every run hard limits on elapsed time, model calls, tool calls, tokens, dollars, and recursion depth. Add a quota for each tenant and a global kill switch. A reliable agent stops or falls back to a known mode instead of looping forever.

Plan for provider outages

Decide what each workflow does when a model provider goes down. Some workflows can switch to another model. Some should queue the work and wait. Some can return a smaller result from fixed code. Write down what changes for the user in each case. Do not switch to a weaker model without saying so.

Run a game day

A game day is a planned exercise where you break your own system on purpose. Inject model timeouts, rate-limit errors with HTTP 429, malformed output, duplicate deliveries, tool outages, slow database responses, expired credentials, and exhausted budgets into your product's staging environment and the agent runner. Check that alerts fire, that the runbooks work, and that the system recovers. Write a postmortem for at least one of the incidents you caused.

You are done when

You can define an SLO, explain its error budget, run a failure drill, and recover safely. You can show that the platform cannot loop or spend money without limit.
